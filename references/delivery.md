# 出片与交付

```bash
python3 scripts/film.py render          # 检查 → 渲染 → 打包，全片约每分钟成片 2.5 分钟渲染
python3 scripts/film.py package         # 只重新打包（已有母版时）
```

## 产出的文件

| 文件 | 用途 |
|---|---|
| `renders/<slug>.mp4` | 母版（很大，约 9 MB/秒）。留着，以后重剪、调色用 |
| `renders/<slug>-upload.mp4` | 上传版：8 Mbps，响度归一到 −16 LUFS。**发平台用这个** |
| `renders/<slug>-preview.mp4` | 720p 预览，发给用户看（约 22 MB/分钟） |
| `renders/cover.png` | 封面 = 视频第一帧 |
| `snapshots/final-contact.jpg` | 成片里每个镜头的中间帧，交付前最后看一眼 |
| `build/package.json` | 时长、镜头数、代码行数、文件大小、响度——帖子里的数字从这里取 |

打包会提醒两件事：第一帧太黑（缩略图会是黑的 → 配 `meta.cover`）；时长超过平台上限。

## 平台时长和画幅

| 平台 | 画幅 | 时长上限 | 备注 |
|---|---|---|---|
| X（普通账号） | 16:9 或 1:1 | **2 分 20 秒** | 超了传不上去；要么 Premium，要么剪短 |
| X（Premium） | 同上 | 很长 | `"platform": "x-premium"` |
| 抖音 / TikTok / 视频号 | 9:16 | 够用 | 竖屏要按竖屏重排机位，见 `scenes.md` |

超时长时的做法：先问用户是不是 Premium；不是就删节点或缩短旁白（改稿 → `film.py audio`），不要靠加速硬压。

上传版通常有一百多 MB，浏览器自动化往往传不了这么大的文件，请用户自己拖进平台。

## 交给用户时说什么

1. 发预览版和封面（`SendUserFile`），不要只给路径。
2. 一段话说清：片长、几段、每段是什么画面。
3. **薄弱处**：哪几个镜头不够好、为什么。
4. **事实**：关键数字和出处；哪些没核到链接；哪些内容故意没讲。
5. 平台限制（时长、画幅）有没有问题。

## 实测帖草稿

用户要发帖时才写。帖子里的数字必须是**实测的**，不是估的。草稿写进工程里的 `post.md`，不代发。

数字从哪来：

| 数字 | 出处 |
|---|---|
| 片长、镜头数、代码行数 | `build/package.json` |
| 从定稿到成片用了多久、渲染几分钟、渲了几次 | `logs/PRODUCTION_LOG.md`（所以过程中要 `film.py log`） |
| 额度/用量 | 当时查到的数，并写明是什么时候查的 |

写法：

- **不夸大**。「一句话出片」只有在真的只给了一句话、没有确认和返工时才能说。有确认、有返工就照实写——如实的过程本身更有说服力。
- 翻车也写：这次检查抓到了什么、改了几轮。
- 结尾留一个人人能接的问题（「你想看下一条做什么题材？」），不要以总结收尾。
- 术语放评论区（three.js、WebGL、numpy），正文说人话（「画面是代码实时算出来的」）。
- 政治性强的题目，正文讲做法，不讲立场；要不要挂节点（国庆等）由用户定，X 上默认不挂。
- 要不要 @ 别人、发布时间，都由用户定。
